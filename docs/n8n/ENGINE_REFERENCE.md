## 2. n8n build gotchas (learned on this instance)

1. **Salesforce node needs BOTH `resource` and `operation`.** For SOQL use `resource: 'search'`, `operation: 'query'`, and put the SOQL in `query`. `validate_workflow` emits a benign warning `Invalid value for "parameters.resource": got "search", expected one of: "account"` — it is a **false positive from the type stub**; the node runs correctly. Don't chase it.
2. **`create_workflow_from_code` does NOT expose the Error Workflow setting.** New workflows land with no failure alerting. After create, set Settings → Error Workflow = `Error Alert (shared)` (`5gSRY0P5hpfLKmFD`) via `update_workflow` `setWorkflowSettings { errorWorkflow: "5gSRY0P5hpfLKmFD" }`, or in the UI. **Silent automation death is how trust dies — always wire it.**
3. **Always `test_workflow` before `publish_workflow`.** Pin the trigger + credentialed nodes with realistic sample rows (pull a few real records via a SOQL read first), run, then `get_execution includeData:true` on the Code node to eyeball the rendered HTML/logic. Only then publish.
4. **`test_workflow` pins credentialed nodes** (trigger, Salesforce, Outlook, HTTP) — the Code/Set/If nodes run for real. So a green test proves your transformation logic, NOT the live SOQL or the send. Confirm the query separately against Salesforce.
5. **Editing a published workflow creates a draft** — the change is not live until `publish_workflow` runs again. `update_workflow` returns success for the draft; don't assume it's active.
6. **Node names are stable references.** `update_workflow` ops target nodes by name; renaming a node (`renameNode`) updates connections automatically, but any `$('Node Name')` expression elsewhere must be updated too.
7. **Data Tables hold config, not state** (cadence tables `fur_cadences` / `fur_settings`, FAQ list). Editable in the n8n UI by whoever has n8n access (IT, not business users). Runtime reads them each run — no redeploy to change a cadence.
8. **`create_workflow_from_code` auto-assigns the WRONG Salesforce credential.** It ignores the `newCredential('name')` and binds the first/default Salesforce OAuth cred — which is **"Salesforce - Prod"** (`dsfRbykdxZPdoIte`). Hit twice building FUR workflows. ALWAYS check the `autoAssignedCredentials` in the create response and reassign every Salesforce node to **"Salesforce - Sandbox"** (`8j2Z1Q8YwHHvR9nn`) via `update_workflow` `setNodeCredential` before running. Building against staging with a prod-bound node would read/write prod.
9. **SOQL has NO `NOW` literal.** `WHERE Next_Touch_At__c <= NOW` deploy-runs but errors `MALFORMED_QUERY: unexpected token 'NOW'`. Inject a runtime UTC timestamp instead — make the query an n8n expression: `... <= {{ $now.toUTC().toFormat("yyyy-MM-dd'T'HH:mm:ss'Z'") }} ...`. (SOQL date literals like `TODAY`/`LAST_N_DAYS` exist, but there is no bare now-literal.)
10. **New custom-field FLS must be ASSIGNED to the n8n integration/running user, not just deployed.** Fields deployed with FLS only inside an unassigned permission set are invisible to the data API for the querying user → both n8n inserts and SOQL fail with `INVALID_FIELD: No such column 'X__c'` even though the field exists (Tooling API `FieldDefinition` still shows it — Tooling ignores FLS, the data API doesn't). Fix: assign the perm set to the n8n cred's user (`sf … assign_permission_set`, or DX `assign_permission_set`). This bit the FUR build — `Borrower_Follow_Up_Integration` had to be assigned to `m.rodriguez@supremelending.com.staging` before any FUR read/write worked.

### WF-1 Path B — "ask the agent for detail" on a vague request (added 2026-08-11, tested)

**Problem found by testing the user guide's FAQ:** a doc request with no named documents (`"please get the docs"`) hit `if (Type==='Document Collection' && docs.length===0) continue;` and was **discarded silently** — no FUR, no Chatter, no work item, no status note, box left filled — AND re-parsed every 5 minutes forever (~700 tokens/run). Claude actually *did* return the reason (`notes: "does not specify which documents…"`); the code threw it away. (This was the design's deferred "low-confidence Chatter-@agent path".)

**Now:** the agent is asked for detail, in two places, and the retry signal is the agent editing the text.
- **`Poll Leads With Box`** also selects `OwnerId, AI_Followup_Status__c`.
- **`Skip Already Flagged`** (new Code node between Poll and Parse): computes an 8-char fingerprint of the request text; if `AI_Followup_Status__c` already starts with `NEEDS DETAIL #<same fp>`, the lead is dropped **before** the AI call — no wasted tokens, no repeat notification. **Editing the text changes the fingerprint → automatically re-armed.** No button, no admin step, no extra field.
- **`Build FUR Fields`** no longer `continue`s on the ambiguity guard — it emits `{needsDetail:true, reason:<Claude's notes>, statusNote:'NEEDS DETAIL #<fp>: name the documents to collect'}`. It also now pairs against `$('Skip Already Flagged').all()` (NOT the raw poll) since the list is filtered.
- **`Needs Detail?`** If → true: **`Flag Lead Needs Detail`** (writes `AI_Followup_Status__c`, visible right next to the box the agent typed in) → **`Chatter Ask Agent`** (HTTP feed-elements, @mentions `OwnerId` with Claude's reason + what to do; `onError:continueRegularOutput`). False → the normal create/reuse path.

### GOTCHA CORRECTION — `setNodeParameter` nests even for a SINGLE SCALAR

Earlier notes implied the JSON-Pointer nesting bug only affected whole-object writes. **It does not.** A single scalar write (`path: '/parameters/customFieldsUi/customFieldsValues/1/value'`) also nested under `parameters.parameters`, leaving the node bound to its OLD expression — hit again 2026-08-12 during the dedupe build. **RULE: use `updateNodeParameters` with `replace: true` for ANY parameter change on ANY node, scalar or not.** (The pointer root is the node, so `/parameters/...` is the correct-looking path — which is exactly why this is so easy to get wrong.)

### 🔴 GOTCHA — NEVER CLEAR A SALESFORCE FIELD WITH A LITERAL `""` (root cause of the twice-regressed `Next_Touch_At__c` fix)

**n8n's update pipeline STRIPS any parameter whose value equals the node default, and `""` IS the default.** So `{"fieldId":"X","value":""}` silently reverts to the keyless `{"fieldId":"X"}` on the **next** `update_workflow` call against that workflow — in a node you did not touch, days later — and the field is then omitted from the PATCH instead of nulled. Observed directly on 2026-08-12: a `value:""` written and verified in `activeVersion` was gone one edit later. The same normalization also strips default-valued keys like `operation:"query"`, `operation:"create"` and `resource:"message"` from untouched nodes (harmless, but it changes the `validate_workflow` warning signature and **looks exactly like nesting damage** — confirm by behavior, not by the warning list).
- **RULE: bind an expression that RESOLVES to empty** — e.g. Code node emits `nextTouch: ''` and the node uses `={{ $json.nextTouch }}`. Non-empty in the JSON, empty at runtime, immune to normalization. **This is precisely why WF-4's `Update FUR` has never regressed while the sub's `Set Escalated` regressed twice.** `Set Escalated` now uses this form.

## 2.13 "Taken out of the cadence" — what pausing a FUR means (concept)

WF-2 (the send engine) only acts on FURs that are **due**: `Status__c IN ('Active','Awaiting Reply','Docs Partial') AND Next_Touch_At__c <= now`. A FUR is "taken out of the cadence" = it no longer matches that poll, so no more automated borrower touches go out.

- **Two levers, both drop it from WF-2's poll:** (1) set `Status__c` to a non-polled value (`Escalated` / `Opted Out` / `Dead` / `Completed` / `Cancelled`), and/or (2) **clear `Next_Touch_At__c`** (blank never satisfies `<= now`). Escalation and close-out do BOTH; WF-4 opt-out/dead do the same.
- **Paused, NOT cancelled/deleted.** The FUR + all history remain; a human owns it via the escalation Task. The whole point of clearing Next_Touch on escalation is so the robot doesn't email "please send your docs" right after a loan officer just spoke to the borrower.
- **Resume (F-13) — DESIGNED, NOT BUILT.** When the human finishes, the intended resume is `Next_Touch_At__c = now + 1 business day` at the SAME `Cadence_Step__c` (re-enters WF-2's poll one business day out, not instantly). Today nothing re-arms an Escalated FUR automatically — resume-on-Task-completion (or a WF-5 rule watching the escalation Task close) is future work. Until then a re-opened FUR needs Next_Touch set manually or Status flipped back to a polled value.

## 3.1 Salesforce gotcha — Long Text Area cannot be filtered OR referenced in a formula

The agent request box `AI_Followup_Request__c` is **LongTextArea**. SOQL `WHERE AI_Followup_Request__c != null` fails `INVALID_FIELD: field ... can not be filtered in a query call`, AND a formula-field `NOT(ISBLANK(...))` fails to deploy (`unsupported field type "Long Text Area"`). To poll for "box is filled" you need a **real Checkbox maintained by a before-save flow** (flows CAN read LTA; formulas cannot). As-built: `Lead.Has_AI_Followup_Request__c` (Checkbox) + before-save flow `Set_Has_AI_Followup_Request` (Decision on `AI_Followup_Request__c IsNull=false` → set the checkbox true/false). WF-1 polls `WHERE Has_AI_Followup_Request__c = true`. Selecting (not filtering) the LTA in the SELECT list is fine. Same pattern needed on Opportunity when the Opp-box branch is built. Flow deploy needs `locationX/locationY` on `<start>` and 2-phase FlowDefinition activation (landed Draft, activated via `activeVersionNumber=1`).

## 5. Follow-Up engine gotchas baked into the design (apply as written when building)

These are the QA-register (§13) findings that are *n8n implementation* concerns — bake them in from the first draft, not as later hardening:

- **F-1 — poll `Awaiting Reply` too.** WF-2's SOQL must include `Status__c IN ('Active','Awaiting Reply','Docs Partial')`. Sends set `Awaiting Reply`; if it's not in the poll, every cadence dies after touch 1.
- **F-5 — mark-then-send idempotency.** Write `Cadence_Step__c` / `Last_Outbound_At__c` **before** the send call. A crash then skips one touch (self-heals) instead of double-texting the borrower.
- **F-12 — no watermark in n8n.** WF-3 marks inbound `tdc_tsw__Message__c` rows with a custom `Chase_Processed__c` checkbox instead of storing "last run" time. Restart-safe, honors the no-durable-state rule.
- **F-4 — auto-reply loop guard.** Never auto-reply to messages with `Auto-Submitted`/OOO headers; hard cap 3 auto-replies per thread per 24h.
- **F-7 — ambiguous match = human.** Multiple record matches on an inbound → Unmatched folder + review ask, never auto-attach. Frequency cap keys on email+phone (person), not record id.
- **F-9 — borrower content is UNTRUSTED.** All AI classify/verify calls return constrained enums/JSON validated in n8n before any action; borrower text is passed as delimited data, never concatenated into the instruction prompt; auto-reply text comes only from templates + FAQ config table.
- **F-13 — escalation resume =** `Next_Touch_At__c = now + 1 business day`, same step (a human just spoke to the borrower).
- **F-14 — re-read checklist state immediately before send;** skip if nothing is missing anymore.
- **Send-time hard gates (WF-2, every send, in order):** record open (Opp closed → close FUR; Lead converted → migrate inline, don't close) → FUR still active → channel consent → **quiet hours 09:00–19:00 borrower-local, Mon–Sat (Sun off)**, TZ from state→TZ map, fallback America/New_York, 9–11am jitter → frequency cap (≤1 SMS + ≤1 email per person / 24h) → 4h dedupe. Quiet hours gate proactive outreach only; reactive replies within ~15 min send anytime; STOP confirmations always immediate.
- **Error path on every WF:** on failure, Chatter post on the FUR + the shared Error Alert workflow notification.

### 5.1 TEST-MODE recipient gate (MANDATORY while building against staging)

**Staging is refreshed from prod, so its Lead/Opp records carry REAL borrower emails/phones. There is no "sandbox email" — the M365 Outlook node and 360 SMS API send for real.** A staging build that sends without a gate will message real borrowers with test content. Non-negotiable guard:

## 9. AI token cost & pre-scale optimization — Path A wording (documented 2026-07-27, NOT yet built)

**Where the tokens go:** WF-1 Path A `Generate Wording` (Information Extractor + Claude) calls the model **once per condition**, re-sending the full system prompt + JSON schema every call (the Information Extractor does not reuse a prompt across items). Measured cost ≈ **~685 tokens/condition** (~560 in / ~125 out).

**Estimate (Sonnet):** ~$0.0035/condition → ~$0.014 per 4-condition opp → **pilot (~200 conditions/day) ≈ $0.70/day; full scale (~2,000/day) ≈ $7/day (~$210/mo).** Small — do NOT optimize for the pilot; premature caching just adds a failure surface.

**Pre-scale optimizations, best first (wire these BEFORE scaling, not now):**
1. **Wording cache keyed on normalized condition text (biggest win).** Encompass conditions are highly templated (same strings across thousands of loans). Cache `normalized condition text → {borrower_ask, doc_type, count, window}` in an n8n Data Table (e.g. `fur_wording_cache`) or a small SF object. First sighting → call Claude; every identical condition after → reuse, **zero tokens**. Persists across runs (unlike prompt caching). Likely removes the majority of calls at steady state.
2. **Switch this step to Haiku (~3–4x cheaper).** Rewriting jargon → one plain sentence is well within Haiku; one-field model change on `lmChatAnthropic`. Cache + Haiku takes full-scale cost to pennies/day.
3. **Batch per opp (one call for all of an opp's new conditions).** Returns an array; cuts repeated prompt/schema overhead within a run. More parsing work — only if volume grows.

**Why NOT Anthropic prompt caching (`cache_control`), even though the prompt is fixed:** (a) n8n's Information Extractor node doesn't expose `cache_control` — you'd have to drop to a raw HTTP Anthropic call; (b) cache TTL is ~5 min, so it only helps within a burst. The Data-Table wording cache gives everything caching would and more, without those limits. Skip prompt caching unless Path A is moved to a raw API call for another reason.

Same applies to WF-1 Path B `Parse Request` and (future) WF-3/WF-4 AI classify calls — a shared normalized-text→result cache + Haiku is the pattern.
